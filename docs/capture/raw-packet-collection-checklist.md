## 最小構成と優先順

まず次の4セッションで、P0項目から採取する。途中でログが分かれても構わない。

1. **S01・通常プレイ**: ログイン先頭 → 本人発言 → 会話メニュー → 数値／文字入力 → 正常終了。
2. **S02・同じNPCの再試行**: 同じ経路の正常完了 → 同じ経路で応答せず終了を待つ → 正常完了。
3. **S03・NPCイベント／インスタンス**: 初回入場 → 同じ経路を複数回 → 視界離脱・再観測 → 別生成の同じマップ。
4. **S04・MOBと状態変化**: 同種MOB複数個体 → HP割合・使用スキル → 死亡／視界離脱 → 再観測。

本人への発言イベント、特殊shop、外見変更等は、該当場面があれば追加する。
1回で全項目を揃える必要はない。**次の最小1本は文字input（01D4→01D5）の正常完了→未応答終了→正常完了**。
0x0B0E／exchange 候補の再試行が自然に取れる場合は Issue #51 をその1本より優先する。
本人入力との照合は20261029-215033-0a6328faで確認済み。数値inputの代表例は20261101-194609-edbe9ab0で追加済み。

## 共通の採取設定・終了方法

1. 現行作業版を起動し、対象ゲームEXEを選択する。
2. 「設定・診断 → 設定」の取得ページで長さ定義を確認する。起動時の既定はプロジェクト直下のPacketLength.txt。
   client/PacketLength.extracted.txtを使う場合は明示的に選択し、そのログのPacketLength.used.txtを残す。
3. 「受信に加えて送信も観測する」をONにする。
4. 「設定・診断 → 設定」の記録ページで「再解析用の生バイトを記録する」をONにする。
5. 観測を開始し、Npcap readyを確認してからログイン／再接続する。最初のマップ入場と本人IDを含める。
6. 操作前後を切り詰めず、先行会話・関連演出・応答後の処理も一緒に記録する。
7. 予定の操作を終え、関連処理が終わったことをゲーム画面で確認してから観測を停止する。
8. セッションフォルダのcapture.jsonl、PacketLength.used.txt、下記の採取メモをセットで残す。

表示用のignorepacket・MOB非表示設定は生バイトの代わりにはならない。整形TXTや解析JSONだけでは再フレーミングできない。
すでに接続済みの途中取得は境界仮定になるため、初回検証はSYNから取得する。
Unknown PacketIDで停止しても未知バイトを読み飛ばさず、そのログと定義を残す。エラー前の数個だけを切り出さない。

本文中のPacketIDは**現行実装で照合する代表ID**。クライアントの版・送信IDシャッフルで異なる場合がある。
表示されるIDを合わせるために定義や生バイトを書き換えない。未知形式もそのまま調査資料とする。
パケット順序はサーバー・ネットワーク次第であり、以下は操作順と検証する対応関係を示す。
無関係な通知が間に入ったら除去せず、そのまま記録する。

## P0・優先して必要な採取

### A01 本人の通常発言とSEND照合

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

操作順:

1. ログインし、現在マップと本人のキャラクターが認識された状態にする。
2. NPC会話を開いていない状態で、通常のオープンチャットへ「KYRIE_S01_01」を1回だけ入力する。
3. ゲーム画面で発言表示を確認してから「KYRIE_S01_02」を1回入力する。
4. 「こんにちは、検証です」を1回入力する。日本語本文・文字コードの照合用。
5. 同じ短文「KYRIE_REPEAT」を2回、各回の表示を確認して送る。
6. 可能なら他プレイヤーにも別の短文を1回発言してもらい、誰が発言したかメモする。

確認する対応関係: SEND通常発言（現行0x008C）→ 本人向け通知（0x008E）、または本人ActorIDを持つ0x008D。
同一取得・フロー・既知の本人ActorID・本文バイト一致・送信後5秒以内の一意候補を確認する。
本文の名前接頭辞や空白は手作業で除去しない。
0x008Dが周囲向けだけで本人には返らない場合もあるので、両方の受信IDが揃うことを必須にしない。

確認結果: 本人はPLAYERとして扱い、SEND根拠ボタンが対応する送信へ移動する。他者の同文は本人SENDへ関連付けない。
連続同文でも各受信が一意なら正常。同時に複数候補が残らなければ「曖昧」になる必要はない。
重複・遅延・欠落の強制再現は合成テストで扱うため、ネットワーク遮断や大量発言は不要。

### A02 手入力なしで本人が発言元になる通知

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

1. プレイヤーに発言させることが画面から分かる既存イベント・NPCを選ぶ。
2. チャット入力をせず、イベントの開始操作だけを行う。
3. 本人の頭上やチャット欄に出た文章、操作したNPC、時刻をメモする。
4. 同じイベントを再試行可能なら、条件を戻してもう1回行う。

本人ActorIDの受信0x008D／本人向け0x008Eと、近傍のSENDに対応する本文がないことを確認する。
ただし、SENDがないことだけではスクリプト起因と確定しない。NPCへの選択応答とチャット入力は別扱いにする。
想定結果は「由来未確定」で、NPC自身のunittalkやタイマーへ変換しないこと。
該当する実イベントがなければ、A01を先に渡し、本項は未採取でよい。

### A03 ログイン先頭・接続切替・再接続

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

1. 観測開始 → ログイン → キャラクター選択 → マップ表示まで操作する。
2. 可能なら別のマップサーバーへ移動する。元と同じIP/PORTか変わったかは解析側で確認する。
3. 通常のログアウト／キャラクター選択へ戻る → 同じキャラクターで再ログインする。
4. 短いNPC会話またはA01の発言をもう1回行ってから停止する。

代表的な対応: TCP SYN → SENDログイン → account echo → キャラ一覧／選択 → map login → マップ情報。
0065、0066、0071、0072／0436、0283、099D／0B72などを、実際に出た版・長さのまま確認する。
接続ごとのID・本文境界・map_loginのsex、現在マップ／XY／キャラ名／Zenyが混ざらないことを確認する。
初回入場時にNPCをまだクリックせず数秒観察すると、初期出現・名前・メタ情報も取得しやすい。

### A04 メニュー全分岐・同じ選択肢への戻り

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

メニューの**表示順**と**操作した順**を両方記録する。番号は画面に出た順で、サーバーへ送る値を直接指定しない。

1. 表示選択肢を上から「1:説明、2:補足、3:終了」のようにメモする。
2. 最初の会話で「1 → 同じメニューへ戻る → 2 → 同じメニューへ戻る → 1 → 戻る → 3」を操作する。
3. 別の会話開始から「2 → 戻る → 1 → 戻る → 3」を操作する。
4. 可能なら3回目も同じ初期状態から行う。各表示順と選択番号をその都度記録する。

戻らない会話なら、再度NPCに話しかけて各項目を別々に採る。異なるメニューへ移った場合は同じメニューと扱わない。
選択肢の文言・順序が変わる場面も、そのままメモする。戻りを作るために未表示の選択肢を送らない。

確認順: RECVメニュー（00B7等）→ SEND選択（00B8等）→ 応答本文 → 同一メニュー再表示 → 次の選択。
確認結果: 同じメニューの戻りはwhile/continueで整理され、未観測分岐は補完されない。
複数応答が完全同一の場合の共有、単一選択肢のラベルなしmenu、異なる応答のswitchも確認する。
全応答同一／単一選択肢のNPCが別にある場合は、そのNPCでも全項目を採る。

### A05 数値・文字入力と同一経路の矛盾

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

1. 同一NPC・同一選択経路から数値入力へ進み、許される値N1を入力して会話を最後まで終える。
2. 同じ開始状態へ戻して同じ値N1をもう1回入力する。
3. 別の許される値N2で1回行う。必要なら文字入力も同様に文字列T1、T1、T2で採る。
4. 入力以前・入力以後の本文、入力値、選択経路を記録する。

数値は0142→SEND0143、文字は01D4→SEND01D5など、要求と応答の対応を確認する。
同一路の本文が状態等により変化した場合は、同じ経路の観測として両方残す。
確認結果: 入力値コメントとインデント付き{}で整理し、変数判定や隠れた条件を生成しない。
入力値を変えたことで報酬や状態が戻らないNPCは、同一初期状態と装わず変化をメモする。

### A06 正常完了・未応答終了・正常完了の統合

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

**同一NPC・同一選択経路**で次の順に採る。

1. 正常側A: next／選択／inputへ通常応答し、会話を最後まで完了する。
2. 未応答側B: 同じ要求まで進み、ボタンや入力を操作せずサーバーから終了が来るまで待つ。
3. 正常側C: 新しく話しかけ、Aと同じ経路・同じ入力値で正常完了する。
4. 可能なら、next待ち・メニュー待ち・数値／文字待ちを別試行に分けて採る。

待機の目安は30〜60秒程度だが、画面上の終了または実際の受信を基準にし、時間だけで終了したと決めない。
終了しない場合は「待った秒数・自分で閉じた」を区別する。タイムアウトを起こすための切断は不要。
サーバー終了後に入力画面が残り、自然に操作可能なら遅れて1回答えてもよい。新規会話を挟む前に行い、実際の操作をメモする。

確認順: 未応答の要求 → 応答SENDなし → 終了close → 遅延応答があれば別記。
正常側の同じ前方部分へ統合され、未応答終了closeだけで本文の相違が増えないことを確認する。
遅延応答後の無関係なwarp／cutin等をclose2の継続へ取り込まないことも確認する。

### A07 closeとclose2・応答前後の演出

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

1. 通常の「閉じる」で終了するNPCを1回最後まで操作する。
2. 「閉じる」を押すとwarp／cutin／効果音等が続く既存NPCで、ボタンを押して後続処理まで採る。
3. 同じNPCで可能なら、閉じるボタンを押さずに待ち、演出がボタン応答前に発生するか観察する。
4. 2と3を別試行として記録する。後続通知の発生後も取得を継続して終了まで残す。

確認順は次の対比。これを操作で強制できなければ、実際の順序だけを記録する。

- RECV close（00B6）→ SEND閉じる応答（0146）→ 関連するwarp／cutin等: close2候補と継続処理後のend。
- RECV close → 応答SENDより前の関連通知: 応答後継続と混同しない。closeと並行・タイマー側の観測として点検。
- RECV close → SEND応答 → 無関係な通知だけ: close2と断定しない。

## P1・NPC配置・演出・複数観測

### B01 同じNPCイベントを3回、操作の待ち時間を変える

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

同じNPC・同じ選択経路・同じ入力値で3回採る。1回はnextや選択の待ちを少し長くする。
会話開始直後から終了後の演出まで記録する。自動再生イベントなら待機操作を増やさず3回観察する。
対象はemotion／effect／解除／unittalk／announce。効果音・BGM・progressbar・viewpointも同時に出たら残す。
他NPCや他プレイヤーが演出した可能性がある場合は、操作していた対象・人数・発生位置をメモする。

可能なら追加1回は、近くの別プレイヤーが同じNPCを操作中に自分は操作せず観察する。
他者が操作した事実はメモし、ログから全通知の原因が確定できるとは扱わない。
会話中・入力待ち・close待ち・会話外・外部対象を分け、反復相違を消さないことを確認する。
会話開始／MAP到着基準は比較専用。手動タイマーはNPC自身の対応演出のみ、時刻は手入力のままとする。

### B02 インスタンス再生成とActorID・名前の省略

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

1. 新しいインスタンスへ入場し、NPCの出現・名前応答を採る。
2. 対象NPCを視界外へ移動して戻り、同じNPCを再観測する。移動先だけで到着と判断せず画面表示を待つ。
3. 同じ会話・イベントを観測する。
4. 通常の方法で別生成のインスタンスへ入り、1〜3を繰り返す。できれば計3生成。
5. マップ名・NPC名が長い場面があれば、その名称と表示をメモする。

生マップ名の3桁英数字接頭辞とNPC名末尾の対応、部分的な接尾辞を含む生文字列を保持する。
同一生成の視界再観測でActorIDが維持されること、別生成のActorIDを単純同一視しないことを点検する。
完全名と省略名、同一マップ名の別世代、他NPC宛て演出を混ぜないことを確認する。
インスタンスの再生成ができなければ、既存生成のログだけでも可。回数不足を記録する。

### B03 OnTouch・class45/139等・warp

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

クリックせず歩いて起動するNPCで、1回目はX方向、2回目はY方向から近づく。
途中で止まれる場面では1セルずつ進み、起動時のプレイヤー位置とNPC位置をメモする。
同一セルに複数NPCがいる場合はその事実も記録する。classが分からなくても採取してよい。
warpのみの経路と、mes等を挟んでwarpする経路があれば別々に採る。
インスタンス内→同一生成内、通常MAP→インスタンス、インスタンス→通常MAPも可能な範囲で採る。

歩行パケットは到着保証ではない。確定できない範囲は最小1・仮最大15の制約で扱い、隠れた正解を補完しない。
class45のwarp／script判定、class139等の推定優先、範囲の片軸だけ確定した場合の補足を確認する。

### B04 外見・表示状態・グループ・称号・待機室

- [ ] 採取済み / [ ] 該当なし / [ ] 未採取

初回出現を含め、NPCが見えている状態でイベントを進め、hide/cloak・外見・名前・称号が変わる場面を採る。
次に視界外へ出て戻り、変化後の状態を採る。可能なら会話なしNPCと会話ありNPCの両方で行う。

### C04 進捗バーの通常完了・途中中断・個体対象表示

- [x] 通常完了の既存例あり / [ ] 途中中断の追加例 / [ ] 09D1個体対象の追加例

通常完了は20261028-012526-0abe69d9で02F0開始 → SEND02F1報告 → 同じ会話元の後続通知を5組確認済み。
同じ正常経路だけを再採取する必要はない。未確認項目が自然に発生するNPCがあれば、以下を別試行で採る。
操作で中断・個体対象表示が発生しなければ未採取のままでよい。

1. **通常側の比較が必要な場合**: NPCを操作して進捗表示を待ち、入力せず表示終了と後続処理を記録する。
2. **途中中断**: 同じ経路で進捗表示中に一度だけ歩行等の通常操作を行う。
   何を入力したかと、バーが消えたか・会話が続いたかをメモする。表示終了まで操作が拒否された場合も記録する。
   何秒で中断できるかを測定する必要はない。操作直後も取得を続け、後続会話・終了まで残す。
3. **中断後の再実行**: 同じNPCを再操作できれば、改めて正常に進める。
   中断前の開始と再実行後の応答が混ざらないことを確認するため、再クリックも含めて採る。
4. **他個体の進捗**: 自分は操作せず、NPC・MOB・他プレイヤーの近くで進捗表示が見えた場面を採る。
   画面上の対象名・種類・位置と、自分が会話中か否かをメモする。
   可能なら自分の進捗と他個体の進捗が同時に見えた例も残すが、対象を推測して記入しない。

確認する代表順序・未確認範囲:

- 正常側: RECV02F0（10byte、色・指定秒数）→ SEND02F1（2byte）→ 同じ会話元の通知。
  SEND02F1はクライアント報告であり、サーバー側の成功・スクリプト条件成立を保証しない。
- 中断側: RECV02F0 → 操作SEND等 → RECV02F2（2byte）の有無 → 実際の後続通知。
  この順序は確認候補。SEND02F1が先行する／中断が来ない場合も削除・並べ替えせず残す。
  操作と中断が近いだけでは、その操作を中断原因とは断定しない。
- 個体対象: RECV09D1（現行定義14byte、対象ActorID・色・指定秒数）と、その前後の個体出現・名前通知。
  この形式は現行デコーダの解釈で、実ログ未確認。02F0の会話元やSEND02F1と自動的に対応付けない。
- 表示が消えた後のwarp・切断・再接続・別NPC開始も残す。02F2だけで会話終了やclose2を生成しない。

確認場所は「会話・コード」の並行・会話外演出JSONにある `progress_observations` と元のパケット詳細。
02F0/02F1/02F2診断は2000行、未解決64経路までなので、省略・追い出しがあれば未確認として扱う。
09D1は進捗演出の元観測で確認し、この開始／応答診断へ混在させない。
会話・通常演出に無関係な通知が挟まっても、生ログには全て残す。

## 採取メモのひな形

capture.jsonlとは別に、同じフォルダへcollection-notes.md等として保存する。

```text
セッションID:
実施日・開始終了時刻:
使用した作業版／取得設定／長さ定義:
対象項目: A01, A04 ...
キャラクター・MAP・NPC表示名・概略XY:
他プレイヤー: なし／あり（何を操作したか）

試行1 開始時刻:
操作: NPCクリック → メニュー[説明,補足,終了]の1 → next → 2 → ...
数値／文字入力: 実際に入力した値
発言入力: 本文と入力回数。入力なしも明記
画面結果: 自分／NPC／他者の発言、音、warp等
応答しなかった箇所: next／選択／input／close、待った時間
終了: 正常終了／サーバー終了／自分で閉じた／切断
初期状態との差: クエスト・アイテム・イベント進行等

試行2 ...
Unknown ID／表示エラーと発生時刻:
未採取項目と理由:
```

実際のPacket番号・IP/PORT・ActorID・送受信順の特定は解析側で行う。分かる場合だけ追記する。
全項目の完了を待たず、セッションIDと対象項目が分かる状態で順に確認へ回せる。
保存後のログは編集せず、そのまま再解析する。

MARiA 互換の 35byte 行 decode は合成用に残すが、鑑定フラグは不明のまま。
