# Npcapによる送信パケット解析

[資料一覧へ](../README.md) · [プロジェクトREADME](../../README.md)

## 利用手順

1. アプリを再起動し、対象EXEを選ぶ。
2. 「設定 → 取得」で長さ定義を確認する。既定はプロジェクト直下の`PacketLength.txt`。
   `client/PacketLength.extracted.txt`を使う場合は明示的に選ぶ。
3. 「受信に加えて送信も観測する」は既定でオン。受信のみの観測も設定で選べる。
4. オフライン検証用の本文を残すなら「設定 → 記録」の「再解析用の生バイトを記録する」をチェックする。
5. 「観測開始」でreadyを待ち、ゲームへログイン／再接続する。ログイン後は移動、会話、
   メニュー選択など、内容を確認できる操作で検証する。
6. 「パケット詳細」の方向がSEND、取得元がNPCAPになる。RAWは既存SQLiteにも保存する。
7. 「設定 → 表示」のRECV/SEND選択で送信側の書式を編集・再読込できる。

Named PipeやDLLは使わず、ネットワーク上の送信バイトを受動的に解析する。
暗号化されていれば平文には戻せない。ログインの一部が読めることだけで、
ゲーム中のすべての送信も平文と判断しない。未知IDや不正長は当該方向の解析を停止する。

## 方向と接続管理

プロセスモードではpsutilで取得したlocal→remoteをSEND、remote→localをRECVとする。
4タプルが逆向きのストリームを別々に再構成し、SYN位置・TCPシーケンス番号・未処理区間・
フレーマー・エラー状態を共有しない。片方向の未知ID停止は反対方向へ波及しない。
RSTは両方向のストリームを閉じ、FINはその方向を閉じる。

手動モードでもServer IPまたはPortでremote側を特定すれば双方向に対応する。
双方が空欄ではSEND方向を判定できないため、送信取得の開始時にエラーにする。
BPFも双方向用のhost/portに切り替える。送受信の両条件に一致する曖昧なセグメントは
推測で分類しない。IPv4/IPv6、Padding除外、プロセス発見前の早期データ保持にも対応する。

Start以前の接続には既存のAttach existing TCP connectionオプションを使えるが、
最初に届いた本文の先頭を境界と仮定する点は送受信共通。検証時はSYNからの取得を推奨する。
現段階では送受信とも選択した同じPacketLengthマップを使う。方向で同じIDの長さが異なる
クライアントへの別マップ対応は未実装。

## 表示定義

`config/send_display.json` は受信用とは別のプロファイルで、29 IDの初期定義を持つ。
キャラクター選択、マップ入場・読込完了、移動、アクション、チャット、NPC会話・選択、
アイテム操作などを表示する。移動座標は現段階では3バイトのpacked値を表示する。
ログインの表示定義にはパスワードやセッショントークンのフィールドを設けていない。

フィールド構造の照合先:
[OpenKoreの送信パケット定義](https://github.com/OpenKore/openkore/blob/master/src/Network/Send/ServerType0.pm)。
これは構造を確認する参考資料であり、対象クライアントでのフィールド互換性を保証しない。
PacketIDシャッフル等がある場合はクライアントと実測に合うプロファイルへ変更する。

受信プロファイルを送信へ流用しない。再読込時は両方向の履歴を各プロファイルで再表示する。
整形ログとUTF-8保存は両方向を含み、未定義の送信IDも@sendとして残る。
表示が未定義でも、長さ定義が正しければ分割とRAW保存はできる。

## ログと再解析

tcp_segment、connection_start、stream_chunk、packet、framing_errorにdirectionを保存する。
オフライン再検証結果にはpacket_counts_by_directionを追加した。以前のログでdirectionが
ないものはRECVとして読み込み、古い記録から未取得の送信を復元したことにはしない。
記録本文を有効にした場合はSEND本文も含まれる。

81テスト通過。受信との分離、同一シーケンス番号、送信再送・順序逆転、片方向停止、
所有プロセス発見前の両方向保持、手動フィルター、IPv6、Padding、RST、方向付きログ再生、
送信プロファイルと受信履歴の同時再表示を検証した。実ゲーム送信の非暗号化判定は未確認。
