## 今回のクライアント調査

対象は `client/unpacked_20261008.exe`。EXEを実行せずPE32/x86の実行セクションを調査した。
SHA256は `bfc513d02d6f175a45a9237bbae9c4d311b195484428ab3e2892a7536ae7ada4`。

4つの即値引数をpushして同じ関数を呼ぶ登録列を検出した。
登録先VAは0x00C16260、登録1,785件、重複を後方優先で解決した結果は1,783 ID。
2件の重複は同じ長さだった。引数の最終属性-1/0/1は報告に残し、送受信方向と断定しない。
静的命令列の抽出であり、分岐条件や実行時のテーブル書換えは評価していない。

- `client/PacketLength.extracted.txt`: 抽出した長さ定義候補。
- `client/PacketLength.extracted.report.json`: 命令位置、引数、SHA256、元定義との差分。
- 元の `PacketLength.txt` は上書きしていない。
- 比較結果は追加108 ID、長さ変更31 ID、抽出候補に存在しない元定義52 ID。
  存在しないことだけを根拠に、旧定義が誤りとは断定できない。
- 0x0C3Cは6バイト固定長。登録命令列はfile offset 0x0081C6F1、VA 0x00C1D0F1。
- 長さ変更31 IDのうち29件は登録属性0、2件は属性1。属性1の変更は
  0x0191の27→86バイトと0x0ADCの10→6バイト。属性の意味と受信実測は別途確認する。

GUIのDefinitions欄に `client/PacketLength.extracted.txt` を指定し、Stop/Startして
新しい接続から検証できる。表示定義JSONは別の仕組みなので、新IDにdisplay undefinedが
出ることと、長さ分割の成否は区別する。長さが変わったIDのフィールド位置も別途検証する。

再生成コマンド（プロジェクトルートで実行）:

```powershell
python -m tools.extract_packet_lengths client/unpacked_20261008.exe --output client/PacketLength.extracted.txt
```

このツールは今回観測した `push×4 / mov ecx,esi / call` の登録方式だけに対応する。
候補が少ない・登録先が複数ある・PE形式が違う場合はエラーで止め、推測した定義を出さない。
任意のクライアントに対応する汎用抽出器ではない。

## 実ゲームでの記録手順

1. アプリを再起動し、必要なDefinitionsを指定する。
2. 再検証用の本文も必要なら「設定 → 記録」の「再解析用の生バイトを記録する」をチェックする。
   通常はオフで、診断メタデータだけ保存する。
3. Startする。ログフォルダーに日時とランダムIDのセッションフォルダーが作成され、
   保存先が画面下部の診断欄に表示される。
4. Npcap capture readyを待ってゲームにログイン／再接続する。
5. エラーが出ても他の接続の取得は継続する。Stopで記録を終了する。
6. 「診断 → 診断ログを保存…」でJSONLを別の場所にコピーできる。
   キャプチャ開始前でも、現在の画面上の診断文をテキスト保存できる。

各セッションには次のファイルを作る。

- `capture.jsonl`: 状態、受信セグメントのメタデータ、正常パケット、停止コンテキスト。
- `PacketLength.used.txt`: 実際に読み込んだ後方優先適用後の定義。正規化SHA256も記録する。

停止レコードはエンドポイント、初期シーケンス、SYN/ASSUMEDの境界種別、TCPの次の位置、
未処理セグメント数、ストリームオフセット、直前16パケットのID・定義長・適用長・開始位置、
停止位置のIDを持つ。通常の診断メッセージには生の本文を出力しない。

本文記録を有効にした場合だけ、各tcp_segmentにdata_hexが入る。フレーマーが停止した後も
対象接続の受信セグメントの記録を続けるため、新定義でその後のデータも再検証できる。
記録開始前やプロセス所有権確認前に失われたデータを回復する機能ではない。
同一受信塊の後半で未知IDが出ても、前半の正常パケットは表示・DB保存するよう修正した。

ファイルは都度flushする。セッションログの上限は64MiB。上限到達や書込エラーは
画面で通知し、キャプチャ自体は継続する。記録の完全性は保証できなくなるため、
再解析結果のsession_end_presentやTCP未処理区間も確認する。画面の診断履歴は200行だが、
保存ファイルは上限内で全履歴を保持する。生バイト記録には実際の通信内容が含まれる。

## オフライン再検証

「設定 → 記録」で再解析用の生バイトを有効にして記録したJSONLに対して実行する。
メタデータのみのログからパケット本文や正しい長さを復元することはできない。

```powershell
python -m tools.replay_capture logs/SESSION/capture.jsonl --definitions PacketLength.txt --output baseline-replay.json
python -m tools.replay_capture logs/SESSION/capture.jsonl --definitions client/PacketLength.extracted.txt --output extracted-replay.json
```

同じ受信セグメントをTCP再構成からやり直し、ID別件数、停止位置・直前パケット、
途中で終わったストリームなどをJSONに出力する。未知IDを飛ばしたり、別の位置へ
自動再同期したりしない。新定義で分割できることだけでは、全フィールドの正しさは証明できない。
CLIが出力するのは解析レポートで、GUIへの履歴再表示機能ではない。

## 今回のエラーの解釈

- 5121番の0x0C3C: クライアント登録に実在し、固定長6。まず抽出定義で検証する対象。
- 6121番の0xACAC・残り4バイト: 以前表示されたID値4631724は0x0046ACAC。
  Little Endianの4バイトaccount IDの先頭と一致するため、ヘッダーなし応答の可能性がある。
  [rAthenaのchar接続処理](https://github.com/rathena/rathena/blob/master/src/char/char_clif.cpp)
  にも接続時にPacketIDを付けず4バイトaccount IDを返す処理がある。
  提供された実ログではこの4バイト値との一致を確認した。
- 3000番の0x5448: LEの先頭2バイトはASCIIのHTになる。HTTP応答等の別プロトコルも
  候補だが、2バイトだけでは判定できない。提供された実ログではHTTP/の先頭を確認した。
  EXEの全ソケットがゲームPacketID形式とは限らない。
- 直前の長さ誤りも候補だが、PacketIDなし応答や別プロトコルを長さ表への架空ID追加で
  解決しない。6121番の先頭4バイトを自動で捨てる処理も、現段階では導入していない。

## パケットDBの保存方式（v0.0.4保存後の開発）

ローカルのパケットSQLiteはWALを試み、同期設定FULLで1パケットごとにcommitする。
バッチの遅延保存や未保存待ち行列は追加しない。既存のpackets列・raw・送受信・source・接続を維持する。
WALを使えない場合は既存のjournal方式でFULL同期を使用する。メモリDBはmemory方式のまま。
診断JSONLのcapture_optionsにはpacket_db_journal、packet_db_synchronous、packet_db_commit、
packet_db_wal_fallbackを記録し、実際に選ばれた方式を確認できる。

WAL方式では使用中にpackets.sqlite3-wal／-shmが作成される。
DBを単体コピーしてバックアップする場合は、アプリを終了してDBを閉じた後に行う。
使用中の補助ファイルを個別に削除しない。停止ボタンはキャプチャ停止であり、DB接続の終了ではない。
生ログのJSONL保存・再解析と、スナップショットからDBを除外する方針は従来どおり。

保存と一覧追加を切り分ける計測:

```powershell
python -m tools.profile_packet_path --events 500 2000 --runs 3 --output logs/packet-path-profile.json
```

一時的な合成パケットとDBのみ使用し、実際のpackets.sqlite3やゲーム取得は使用しない。
同環境の2000件・3回中央値ではrollback journal約3705ms、WAL＋FULL約757ms、
メモリDB約5.6ms、一覧セル追加約87ms。件数・別接続からの可視性・閉じた後の再読込を別途検証した。
これは対象PCのDB／表操作の分離測定であり、解析・全GUI・実機・ディスク障害時の動作を含む値ではない。


## DB保存エラーとGUI処理状況（v0.0.4後の開発）

診断画面に、このウィンドウでの取得側発行数・GUI未受付数・GUI受付数・処理完了数・
DB保存確認数・DB保存未確認数を表示する。取得側発行数はライブ取得とPipeからの通知数であり、
直接読み込む保存ログはGUI受付数にのみ加算する。件数は取得の再開でもリセットしない。
GUI未受付は取得側通知数からGUI受付数と受付拒否数を引いた値であり、TCP欠落数や保存待ち件数ではない。

SQLite保存エラー時は取得を停止し、以後同じウィンドウからの取得再開を禁止する。
受信済みと、停止前にQtへ発行済みの通知は画面内で処理し、DB保存未確認として数える。
自動再試行は重複保存を避けるため行わない。失敗したトランザクションはrollbackを試みるが、
commitの結果を断定できないため「未保存」ではなく「未確認」と表示する。
診断JSONLには例外型・SQLiteエラー番号・失敗時点の件数のみを記録し、例外本文やRAWは含めない。
停止後に届く通知による最終件数はGUIで確認する。保存ログの再解析でもDBエラー後は処理を中断し、
再解析完了やプロジェクト保存を有効にしない。

画面内記録は永続保存の代替ではない。必要な表示・解析結果を閉じる前に書き出し、
生パケットを再解析する場合は取得前に生ログ記録を有効にする。
パケット通知の上限は下記のとおり。生産側を待たせるバックプレッシャーと、長時間取得の全履歴保持制限は未実装。


## GUIへのパケット通知上限

ライブ取得とPipeが共有する待機通知を4096件、RAW合計16 MiBまでに制限する。
どちらかを超える通知はQtへ送らず、最初の超過から以後の通知も拒否する。
GUIスレッドが通知を処理できた時点で取得を停止し、「取得不完全」と受付拒否件数を表示する。
上限内に受付済みの通知はDB・解析・表示まで処理する。同じ画面での取得再開は禁止する。
TCP再同期や欠落内容の補完、自動的な続行は行わない。

取得側発行数は拒否分も含む通知試行数。拒否数はGUI配送できなかったパケット数であり、
TCP欠落や生ログの欠落とは異なる。生ログは取得側で先に記録されている可能性がある。
JSONLのpacket_delivery_overflowは停止処理時点の件数を記録する。並行コールバックにより
最終件数が増えた場合はGUIの累計を参照する。
RAW制限にQt・Pythonの管理領域、現在処理中の1件、処理済み履歴は含まない。
status・接続一覧の通知を制限するものでもない。

合成計測（実通信・DB・解析なし）:

```powershell
python -m tools.profile_packet_delivery --output logs/packet-delivery-burst-profile.json
```

GUI受付を止めた間に1万件を生成する。同PCの4096バイト通知では、上限制御なしの
RAW保持40,960,000 Bに対して制御あり16,777,216 B、受付4096件・拒否5904件だった。
Python追跡メモリのピークは約43.8 MBから17.9 MB。Qt内部はPython計測に含まれず、
プロセスRSS差分はアロケータと計測順序の影響を受けるため厳密な上限とは扱わない。
この計測で長時間運用全体のメモリ上限や実機での処理速度を保証するものではない。


## 画面終了時の通知排出

終了要求を受けた画面は新しいパケットの受付を閉じ、取得を停止する。
受付済みでGUIへ未配達の通知は、DB・解析の処理が終わるまで待つ。
受付数を増やしてからQtへ発行する途中に終了が重なった場合も、この待機数で保護する。
保存・生成スレッドと子画面の読み戻し／保存処理の終了後に、診断ログとDBを閉じる。
DBを先に閉じることによる見かけの保存エラーや、閉じたDBへの後続書込を防ぐ。

終了受付停止後の通知はQtへ送らず、shutdown_rejectedとして受付拒否総数の内数に記録する。
この意図的な終了時拒否だけではoverflowedにしない。通常の「停止」は受付を閉じる操作ではなく、
受付済み通知や旧取得世代のコールバックを処理でき、後から取得を再開できる。

終了中にDB書込が失敗した場合も、診断を先に残してからログ終端を記録する。
ログがまだ開いていれば、packet_delivery_shutdownに終了時点の処理・保存確認／未確認・受付拒否件数を記録する。
手動停止等でログが既に閉じている場合は、そのログを開き直さない。
一度閉じた画面に遅れて届く直接呼出しは、DBやウィジェットへ反映しない。
