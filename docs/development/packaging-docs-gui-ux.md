# 実行形式・文書分割・GUIユーザビリティの検討

[資料一覧](../README.md) · [開発計画](development-roadmap.md) · [NOTICE](../../NOTICE)

日付: 2026-11-06（日本時間）。**実装ではなく方針検討**。コード・取得契約・生成規則は変えない。
次の着手単位への取り込みは [development-roadmap.md](development-roadmap.md#次の着手単位) を参照。

## 現状（点検結果）

| 領域 | 現状 | 主な制約 |
|------|------|----------|
| 起動 | `python main.py`（venv＋`requirements-lock.txt`） | Windows＋Npcap＋権限が実取得の前提 |
| 配布物 | private ソースZIP（`tools.build_snapshot`） | 公開ライセンス未確定。logs／DB／client EXE／`.reference` 除外 |
| 文書 | `docs/guide`＝操作、`npc`/`mob`/`capture`＝契約＋操作混在、`development`＝方針 | 目次は読者軸が弱い。操作ガイドに古い検証履歴が残る箇所あり |
| GUI | 作業／設定・診断／出力メニュー＋用途別タブ | ショートカット・Help/About・初回導線が薄い。`main_window` が大きい |

`build_snapshot` の `ROOT_FILES` に `LICENSE` があるがリポジトリに実ファイルは無い（存在時のみ同梱）。公開配布のブロッカーは LICENSE 欠落だけでなく [NOTICE](../../NOTICE) の方針未確定。

## 1. 実行形式ファイルへのコンパイル

### 結論（推奨）

1. **当面の正本はソース＋venv**（現状維持）。再現性・辞書更新・表示JSON編集に合う。
2. **EXE はメンテナ向け private 試験**に限定し、GitHub 公開 Release や利用者向け配布とは分離する。
3. **公開 EXE／インストーラは条件付き後段**（ライセンス・Npcap・参照資料の再配布条件が揃うまで着手しない）。

### 候補比較

| 手段 | 向き | 主な懸念 |
|------|------|----------|
| 現状（venv） | 開発・検証の正本 | 利用者が Python を用意する必要 |
| PyInstaller **onedir** | Windows private 試験向き | Qt プラグイン／Scapy データ。onefile は起動遅延・展開失敗が増えやすい |
| Nuitka | 起動・配布サイズの改善候補 | ビルド時間・メンテコスト。まずは PyInstaller 試験の後 |
| cx_Freeze / Briefcase 等 | 今回は優先しない | 知見・CI コストに対する利益が薄い |

Npcap はいずれの EXE でも **外部導入**が現実的（管理者権限・アダプター選択・再配布条項）。EXE 化しても「ダブルクリックだけで取得開始」にはならない。

### 同梱してよいもの／いけないもの

- 可: `main.py` 相当のエントリ、`config/*.json`（個人設定を除く）、同梱 `PacketLength.txt`、表示・生成用 JSON、NOTICE／依存ライセンス一覧。
- 不可（現行スナップショットと同じ）: 生ログ、DB、ゲーム client EXE、`.reference` 原資料、`config/user_settings.json`、作業用 ignorepacket 個人値。
- 要確認: クライアント由来の名称辞書を EXE に焼く場合の再配布条件（現状ソースZIPと同趣旨で慎重に）。

### 段階

- **A（文書）**: README／本メモで起動経路を明記。公開 EXE を約束しない。
- **B（任意・Windows）**: private PyInstaller onedir の試作と起動チェックリスト（観測開始／停止、生ログ再解析、診断保存）。CI の Linux offscreen では代替しない。
- **C（条件付き）**: ライセンス確定後の署名付き配布・更新手段。別 Issue で扱う。

## 2. 利用者向け／開発向けドキュメントの分割

### 結論（推奨）

**いきなりディレクトリを全面移動しない。** まず目次と誘導を読者軸で分け、操作ガイドから「検証履歴」を分離する。仕様契約（npc／mob／capture）は共有の正本のまま残し、各先頭に操作向け要約を足す方向が安全。

### 読者軸（提案）

| 入口 | 含むもの | 含めないもの |
|------|----------|--------------|
| 利用者 | 導入、GUI操作、再解析、採取チェックリスト、限界・NOTICE | テスト件数履歴、プロファイル計測コマンドの詳細、MARiA差分表全文 |
| 仕様契約 | 観測意味・生成境界・未対応一覧 | 「いつ何件通したか」の時系列 |
| 開発 | roadmap、progress-notes、working-agreement、テスト方針、hook設計 | 日常操作の手順書の重複 |

### 段階

- **A**: [docs/README.md](../README.md) を「利用者」「仕様契約」「開発」の3入口に再編（本PRで着手可）。
- **B**: `guide/*` の古い実装・検証段を [progress-notes](progress-notes.md) へ退避。操作手順だけを残す。
- **C**: 必要なら `docs/user/` 等への物理移動。相対リンク・スナップショット allowlist・リンク検査を同PRで。

DEVELOPMENT.md は作業メモの置き場のまま。仕様の代替にしない合意は維持する。

## 3. GUI ユーザビリティ

### 結論（推奨）

機能密度は復元用途として妥当。次は **発見性** と **診断への導線**。簡易モードや大規模レイアウト改修は、観測根拠・生成契約を壊さない範囲で後段。

### 観測されたギャップ

- メニューにヘルプ／About（版番号・NOTICE）が無い。
- 開始／停止／生ログを開く等のキーボードショートカットが無い。
- 初回の Npcap・PacketLength・生バイト記録オプトイン説明が設定画面と docs に分散。
- エラー時はステータスが「診断を確認」と促すが、ワンクリックで診断を開く導線が弱い。
- `gui-workspace.md` に「これから追加するビュー」調の古い段が残る（実装済み内容と重複）。

### 段階（working-agreement の P2 に相当）

- **P2-1（小さく・回帰しやすい）**
  - ヘルプ → 操作ガイド（docs パスまたは同梱HTMLは後で）／About（`version.__version__`・NOTICE要約）
  - 主要ヘッダーボタンの短い toolTip
  - 取得エラー／DB障害ステータスから診断ダイアログを開く
- **P2-2**
  - 観測開始／停止・生ログを開くショートカット（フォーカスが入力欄のときは上書きしない）
  - 初回チェックリストダイアログ（**設定値を黙って変更しない**。案内と設定画面へのリンクのみ）
- **P2-3（任意）**
  - 「観測中心」「復元中心」のタブ初期表示プリセット（user_settings に保存可）
  - layout／main_window の責務分割は UX 変更と同時に小さく進める

対象外: 未観測条件の自動補完、取得契約の緩和、推測による命令増加。

## 推奨の着手順

1. 文書: 目次の読者分割＋本検討の roadmap リンク（低リスク）。
2. GUI P2-1（Help/About・診断導線）— 利用者の迷いを先に減らす。
3. private EXE 試験は Windows メンテナ環境で任意（公開と切り離す）。
4. 公開 EXE／物理 docs 大移動は条件または明確な利用者指示の後。

## 非目標

- 「全MARiA互換」や公開ストア配布を本検討の完了条件にしない。
- Linux CI の offscreen 成功を Windows EXE／Npcap 実機の代替にしない。
- ソーススナップショット v0.0.10 の自動作成は利用者指示待ち（既存方針）。
