# 通常ショップの観測

[資料一覧へ](../README.md) · [プロジェクトREADME](../../README.md)

NPCタブ下側の「ショップ観測」で、一覧通知ごとに商品と価格を確認できる。
基本価格・割引価格・種類を分けて保持し、新形式の外見値・装備位置値も残す。
「根拠パケット」は選択した一覧通知へ移動する。
「ショップJSON保存…」は全一覧・対応根拠・解析問題・source_sessionsを保存する。
表示JSONの再読込では観測内容は変わらない。

## レイアウトとIDの意味

初期実装は32bitクライアントアイテムIDの次の2形式に限定する。

- RECV 00C6: 総長4バイトヘッダー、1商品13バイト。
  価格u32、割引価格u32、種類u8、クライアントIDu32。
- RECV 0B77: 総長4バイトヘッダー、1商品19バイト。
  クライアントIDu32、価格u32、割引価格u32、種類u8、外見u16、装備位置u32。

総長・項目の割り切れ・項目数・IDを検証する。11バイト形式への自動切替はしない。
長さだけからクライアント版を確定できるとは扱わない。対象版の検証が必要。
同じIDの重複掲載や0価格は観測値として保持し、勝手に統合・価格補完しない。

受信IDはclient_item_idとして保存する。表示用IDをサーバーDBのアイテムIDへ
自動変換しない。ID対応と配置を確認した場合の[shop/callshop候補生成](shop-export.md)を追加した。
売却一覧、キャッシュは対象外。拡張barter（RECV 0x0B56）は別経路で観測し、
[shop/callshop候補生成](shop-export.md)のコメント付き`- barter`候補へ出す。

## 対象NPCの対応

RECV 00C4の対象IDを取得世代・接続フローごとに保持し、一覧1件で消費する。
SEND 00C5で同じIDへの購入選択を確認できた場合はselector_and_buy_reply、
選択画面だけの場合はselector_onlyとして、確度を区別する。
会話終了通知の直後、同じフローで2秒以内に00C4なしで一覧だけが届いた場合は
after_close_listとし、終了した会話へsame_flow_after_closeで結びつける。
それ以外の一覧だけではunresolvedとし、近傍NPCや無関係な台詞へ推測で割り当てない。
対象ID0を実在NPCや仮の配置へ置換しない。

売却選択、別対象への応答、マップ切替、新しい会話、終了操作、対象消滅、
世代切替、不正一覧で関連付け待ちを破棄する。60秒超過や時刻逆行でも破棄する。
遅い応答は未解決になる場合があるが、古い対象への誤接続を避けるための保守的な制約。
NPC配置は選択画面を観測した個体と、一覧時点の個体が同じ出現記録のときだけ付加する。
後から現れた同じIDのNPCの情報を借りない。

全てcause_confirmed=false。明示された購入選択は関連付けの根拠であり、
会話やイベントの起因・ショップの実装条件を復元したことにはしない。

## 上限と再解析

一覧は最大1000件、商品合計20000件、1一覧2048商品、関連付け待ちは64フロー。
上限・不正データは解析問題へ記録し、部分商品一覧を正常として採用しない。
取得世代をまたいで待ち状態は引き継がない。保持済み一覧は世代別の根拠として残る。

```powershell
python -m tools.analyze_shops logs/SESSION/capture.jsonl --definitions client/PacketLength.extracted.txt --output logs/SESSION/shops.json
```

CLIも同じデコーダーと状態管理を使用する。GUIの1件／複数ログ読み戻し・
プロジェクト再開でも、生ログからショップ観測を再構築する。
元ログと長さ定義へのCLI出力上書き、元ログへのGUI保存は拒否する。

これは対象クライアントでの実測確認の代わりではない。

接続・世代・売却／取消・期限による対応解除、未解決一覧、GUI表示・保存・根拠を検証した。
合成した双方向TCP生ログからのCLI再構築も、GUIの商品・価格・NPC対応と一致した。
日本語のオフスクリーン画面も確認済み。
既存2実ログのショップ一覧は0件、ショップ解析問題も0件。
ショップを開く追加ログでの実機確認、DBのID対応確認、shop宣言出力は今後の対象。
