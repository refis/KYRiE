# 複数会話の観測経路統合

[資料一覧へ](../README.md) · [プロジェクトREADME](../../README.md)

## 未応答終了と正常継続の一本化

タイムアウト疑いのcloseと、その後の終了応答を経路比較へ入れず、元の未応答要求までを前方一致で照合する。
同じNPCの正常継続観測と本文・入力要求が一致した場合、その終了側を部分観測として同じグループへ収める。
正常継続側に観測された応答・分岐だけを生成し、未応答側の選択値・入力値や隠れた条件は補完しない。
close待ちの再closeは、元のclose要求までを比較し、正常側のclose/close2継続を保持する。

JSONのcontributionsには元の終了会話とタイムラインを保持し、partial_observation=trueとnormalizationを付ける。
timeout_normalizationsに照合方法・一致トークン数・継続側の出典を保存する。元のstepsや返信リンクは変更しない。
部分観測を完全な反復試行として数えず、演出の反復一致率にも加えない。統合OFFでは従来の終了疑いを表示する。

正常な対応経路がない、本文や要求が違う、取得品質に他の問題がある場合は統合しない。
要求前のクエスト・所持品・Zeny等は、正常継続側と位置・種類・内容・件数・順序が一致する場合に限り統合できる。
参照パケット番号や取得時刻そのものは照合キーにせず、会話内の位置と受信値を比較する。
クエスト命令は正常継続側だけから出力し、終了側の重複命令を追加しない。
要求後の関連通知、並行演出・外部演出がある終了側は、引き続き要確認として保留する。
未観測の後続や他ユーザー由来の演出を、close削除だけで正規経路へ取り込まない。
全393テスト通過。各入力種別・close待ち、非一致保留、入力順非依存、元観測保持、GUI切替と一括出力を検証済み。
要求前の関連観測照合を含め全396テスト通過。状態・値・件数・順序の相違、クエスト命令の重複防止も検証した。

## 外部NPC演出の照合

会話中に別の既知NPCへ届いた演出も、external_candidateという独立した観測列で照合する。
対象NPCの配置・名称、演出内容・有無・順序を比較し、不一致を既存の演出警告と根拠JSONへ残す。
対象ActorIDは取得・再出現で変わるため、観測ごとのIDを根拠に保持しつつ配置情報を比較に使う。
反復一致でも会話NPCが呼び出したと確定せず、他ユーザー操作が繰り返し混入する可能性も残す。
外部命令候補は本文の実行列へ挿入せずコメントとして列挙し、after_step_indexとPacket番号で受信位置を追える。
既存の会話矛盾ブロックや入力待ちの並行演出とは区別する。

「会話・コード」で「同一NPCの観測経路を統合」を有効にすると、現在のワークスペース内の
対象会話をまとめたAuriga本文候補を表示する。既定は従来の単一会話出力。
「コード保存…」は現在の出力方式に従う。「会話JSON保存…」は従来の単一会話群と時間経過、
「統合JSON保存…」は全統合グループ・除外理由・元会話・根拠・コード候補を保存する。
時間経過の表と「根拠パケット」は選択中の単一会話に対応する。
統合した別会話の根拠は「根拠JSON」または統合JSONで確認する。

## NPCの識別範囲

- マップ名・名前・外見・XY・向きが揃った場合は、同じ配置として別ログ／取得世代の候補を集約する。
  ActorIDは接続ごとに変わり得るため、別ログのActorID一致だけでは関連付けない。
- 初期マップ名が不明でも、NPCの名前・外見・座標・向き・受信接続・マップ世代・出現記録が
  確認できれば、同じログ／取得世代の同じActorID・出現記録内に限ってまとめる。
  scope=capture_entityは別ログへ広げない。
- その他の未識別NPCは除外する。同じ名前だけのNPC、別座標・外見・向き、再出現を無理に統合しない。

同じ配置の一致も、元のNPCスクリプトやイベント状態が同じだった証明ではない。
同名・同位置の複製、サーバー更新、クエスト状態の違いは通信だけで排除できないため、
出力は観測候補として元ログ・取得時期と併せて確認する。

## 経路と不一致

会話開始が観測され、closedまたはmap_changedで終了し、解析問題・時刻不正・途中取得等の
品質フラグがない会話を対象とする。未完了・中断・取消の会話は統合しない。

表示文章を再解析せず、既存の意味イベントから共通の接頭経路を作る。
mes、next、clear、cutin、close、menuと、隣接する正しい次へ／選択応答を使用する。
メニューは選択肢の内容と並びが一致する場合にだけ共有し、選択番号ごとに観測した続きを置く。
末尾区切りを除去した選択肢配列で比較する。未選択の分岐はコメントとendのまま。
入れ子の選択肢も保持し、カットイン状態を各分岐へ引き継ぐ。

同じ選択経路で台詞や命令が異なる場合、各観測を独立したインデント付きの{}ブロックで併記する。
開始直後の台詞が異なる場合も、最初から各ブロックを並べる。
共通する部分までは一度だけ出力し、不一致以降の各続きを保持する。
短い終了経路と長い経路、異なるメニュー構成も同じ原則で扱う。
conflictsと各ノードのevidenceに、両方の観測と元パケットを残す。

数値／文字入力の応答後も、観測した続きをインデント付き{}で出力する。
ブロックの直前に「// 入力数: 12」「// 入力文字: \"文字列\"」のようなコメントを付ける。
引用符・改行などはエスケープし、コメントからコードへはみ出さないようにする。
同じ入力値で異なる会話があれば、その内側にも別観測ブロックを置く。
元会話と時間経過もcontributionsへ保存する。
マップ移動も実際の終端パケットを保持するが、warp命令を推定しない。

これらの{}は編集・判定補助用の**無条件ブロック**であり、実行時に観測例を選別するものではない。
起因判定、元変数名の判定、隠れた条件式の生成は対象外。if等を推測して追加しない。
複数のclose/endを含む観測例が並ぶことがある。元の条件分岐を自動復元したコードとは扱わない。

## 選択肢の出力

複数選択肢は一時変数へmenu戻り値を代入し、その変数でswitchする。

```text
set '@menu,menu("選択肢1","選択肢2");
switch ('@menu) {
    case 1:
        // 観測した続き
        close;
        end;
    case 2:
        // 未観測の分岐
        end;
}
```

`'@menu`（rAthenaは`.@menu`）は編集用の一時変数であり、隠れた元変数名の推定ではない。
選択肢は`:`連結ではなく、各選択肢をダブルクオートで並べる。
各caseの本文をさらにインデントし、入れ子のswitchも同じ形式にする。
単一選択肢、または全選択肢が観測済みで末尾まで同一なら、switchなしの`menu "…","…";`から続行する。
未観測caseとcloseで止まるcaseは`end;`のみ（直後の`break;`は付けない）。close2／callshop経路は`end;`の後に`break;`を残す。
この方針は単一会話出力と統合候補の両方に適用する。

これは現在対応する**会話本文**の統合であり、アイテム授受・クエスト・会話外演出を含む
完全なNPCコードではない。特殊な台詞タイプもエミュレータ命令へ完全移植したとは扱わない。
タイマー・待機命令も生成しない。各観測の時間差は別のtimelineに保持する。

## 書式と互換性

config/auriga/dialogue.jsonで文面・構造を設定する。
indent、block_open/block_close、switch_open、case、break、alternatives/alternative、
input_number_observation/input_text_observationが新形式の書式。
indentは1～16文字の空白／タブ。テンプレートのリテラルの波括弧は{{と}}で記述する。
古いカスタムプロファイルに新キーがなければ、同梱JSONから構造用の既定値を補う。
旧merge_conflict/merge_inputは互換用として読めるが、新形式のブロック出力には使用しない。
merged_header/merge_boundary/merge_unavailableの未指定時は既存のheader/pending/ambiguousを利用する。
文面を変更して「生成形式を再読込」を押せば候補を再表示する。
統合の判定は書式の変更に影響されない。
GPA/GPMの名前付きラベルは新形式では生成しない。入力用gpa変数は生成器の仮名であり元変数名ではない。
空のmap表示はマップ名未観測を意味する。

## ログからの再構築

```powershell
python -m tools.merge_dialogues logs/SESSION1/capture.jsonl logs/SESSION2/capture.jsonl --definitions client/PacketLength.extracted.txt --output logs/merged-npcs.json
```

同一の指定ファイルは重複読み取りしない。同じログを別名でコピーした場合の同一性は判定しない。
[GUI読み戻し](../guide/offline-replay.md)は1ログを別ウィンドウへ再構築する。
[複数ログ比較](../guide/multiple-log-replay.md)からGUIでもログ間の統合を行える。CLIも引き続き利用できる。
入力ログ・長さ定義への上書きは拒否する。元のフレーミングを変えず、未知IDを再同期しない。

出力はschema_version=2。groupsにNPC識別範囲、ノードと選択肢、入力応答、元会話とtimeline、
元パケットのsource_ref・取得世代・会話番号・パケット番号・時刻を持つ。
excludedに除外理由、sourcesに再生時の定義ハッシュとTCP診断を保存する。
condition_generation=excludedとし、server_conditions_restored/timers_restoredはfalseを維持する。

1回の処理は最大2000入力会話、1会話2048ステップ、元会話群100000ステップ、
元会話JSON相当32MiB、経路ノード100000（別途グループごとにroot）を上限とする。
超過した会話は全体を除外し、理由を残す。入力会話数で打ち切った場合は
input_capacity_reached=trueを出力する。
コードは1候補4Mi文字、処理待ちの展開100000件を上限とする。
超過時は括弧が閉じていない部分コードを返さず、その候補のaurigaをnullにして
generation_errorsへ理由を残す。統合根拠JSONは保存する。

## 演出の反復観測チェック

同じNPC識別範囲で、演出を除く会話内容・選択肢・入力値・終了状態が一致する
完了済みの試行同士を比較する。エモーション、エフェクト、効果音、カットインの
有無・回数・値・順序・会話内の位置を照合し、相違があれば要確認として表示する。
片方に演出がない場合も比較対象。重複指定した同一観測は試行数に加算しない。
別の選択肢・入力値・台詞や、取得品質の悪い会話は同じ試行として比較しない。
別マップや別NPC識別範囲の観測も混ぜない。

GUIの単一会話／統合表示と保存コードに注意を表示し、統合JSONの各groupに
`presentation_check` を保存する。comparisonsのstatusは単発の
`insufficient_observations`、反復一致の `consistent_observations`、
不一致の `conflicting_observations`。variantsに演出列と、演出がない試行を含む
source_ref・取得世代・会話番号・元パケット参照を保持する。
`after_token_index` は演出を除いた経路内の直前トークン番号（開始前は-1）。
通常のパケット時刻の揺れは比較せず、効果音の繰返し間隔など通知の引数は比較する。

不一致から他ユーザー操作が原因とは断定しない。反復一致でも会話由来と確定せず、
全て `cause_confirmed=false` とする。多数決で演出を除去したり、条件式を生成したりしない。
元観測と、従来のインデント付き不一致ブロックを残す。
`analyze_dialogues` も `presentation_checks` と注意付き本文候補を出力する。
単一ログの再解析はそのログ内、`merge_dialogues` は指定ログをまたいで比較する。

エフェクトはMARiAの `0x019B` / `0x01F3`（10バイト、対象IDと32bit効果値）を追加した。
他ユーザーの通知が混ざる可能性を考慮し、会話中のNPCと対象IDが一致する場合に限る。
入力待ち中の並行演出の比較は次節を参照。会話外の演出の反復比較は未対応。
全207テストで、有無・値・順序・選択肢の分離・根拠・GUI/JSON保存を確認した。
TCP形式の合成ログ3件から同じ選択の演出差を検出し、別選択とは分離することも確認した。
既存の実ログ2件は生成コードが従来と一致し、演出矛盾は0件だった。
これは演出を繰り返し観測して一致したことを意味しない。今回の実ログには比較対象の演出がない。

### 入力待ち中の並行演出

入力待ち中の同じ対象NPCのエモーション・エフェクト・効果音を
`Conversation.parallel_presentations` に保持する。カットインは対象IDを含まないため
現在の会話フローの並行観測として保持し、`target_observed=false` を明記する。
本文のstepsへ挿入しないため、プロンプトと応答の対応・生成命令の順序は変えない。
時間経過表には `step_index=null`、`track=parallel_presentation` の行として元順序で表示する。
入力待ち全体の時間はプロンプトから応答までの値を維持する。

反復比較では、同じ入力待ちの演出の有無・値・回数・順序を含める。
variantsの演出に `track=input_wait` と入力待ちのアンカー番号を記録し、
根拠には元パケットとプロンプトのstep番号を残す。本文を無条件ブロックへ分ける原因にはせず、
演出照合の注意表示と根拠で扱う。演出の時刻・取得順が入力待ちの範囲を外れる観測は統合対象外。
入力待ちの長さが異なると演出の観測機会も変わるため、不一致は原因の証明ではない。
sleep/OnTimerや並行処理コードは生成しない。

会話外・別対象・過去の取得世代の演出は、特定の会話へ帰属させず
`presentation_observations` に対象ID・接続・世代・時刻・値を保存する。
既知の対象は観測時点のentity_kindとNPC配置を付加するが、未解決対象をNPCとは断定しない。
会話画面の「並行・会話外演出」で確認でき、会話が0件でも表示・会話JSON保存が可能。
会話外の演出は比較基準の操作が特定できないため、まだ反復比較やコード生成を行わない。

本文外の演出は全体10000件、本文と並行演出は合計1会話2048件を上限とする。
超過は `presentation_dropped` と診断へ記録し、当該会話の照合も品質不足として除外する。
入力待ち中の不正通知も問題を残し、正常な会話応答の取り込みは継続する。
旧JSONでparallel_presentationsがない場合は空列として読み込める。

全209テスト通過。選択・次へ・数値・文字入力それぞれで、並行演出の有無の検出、
応答の対応維持、本文への演出命令の不挿入を検証した。
不正な観測時刻の除外、保持上限、スナップショットの独立性、GUI表示も確認した。
既存2実ログは本文候補が従来と一致し、今回対象の並行・会話外通知は0件だった。
実ゲームでの今回の並行演出の取得・反復比較は未検証。

## 反復メニューの出力

同じメニューへの観測済みの戻りは、[while/continueの編集用候補](dialogue-menu-loops.md)へ整理する。
入力・別メニュー・未応答等の境界は跨がず、元の統合ノードと根拠は保持する。
全選択肢の応答が同じ本文から同じ次メニューへ合流する場合は、共通本文をまとめてから
次メニューの観測を集約する。その先の観測範囲の違いだけで本文やwhileを分割しない。
