# ログイン先頭account echoとキャラクター情報

[資料一覧へ](../README.md) · [プロジェクトREADME](../../README.md)

## 20261027-193248-fcdc039cの原因

0071にはlasagna.gatが生ログに記録されていた。取りこぼしや0071の構造変更ではなく、
その前にキャラクターサーバーが返すIDなしのaccount ID 4bytesを、未知PacketID 0xACACとして
止めていたため、後続の0B72と0071へ到達できなかった。
[Auriga公式char.c](https://github.com/auriga/auriga/blob/master/src/char/char.c)にも
WFIFOL(fd,0)=account_id、WFIFOSET(fd,4)の返送処理があることを照合した。

修正はTCP再構築後・ゲームパケット分割前の初期プローブに限定する。
SYNから取得した同一フローのSEND 0065（17bytes・有効なsex）を解析でき、
RECV先頭4bytesがそのaccount IDに完全一致した場合だけ、1回のaccount echoとして消費する。
分割・結合セグメントに対応し、4bytesを待ってから照合する。
途中取得の推定境界では適用しない。後続や途中の未知IDを探索・再同期しない。
不一致・未確認のaccount echo・再接続後の古い情報は従来通り保護する。
診断にはaccount_echoとbyte_count=4、照合根拠を記録し、payloadを載せない。
framerのoffsetは、このハンドシェイクを除いたゲームパケット列の位置となる。

この照合にはSENDログイン要求も必要。RECVだけの取得や、要求より前に受信を処理した結果
すでに停止したストリームを、後から読み飛ばして再開する処理は追加していない。
生ログの取得順と両方向情報が揃えば、GUI読み戻し・CLI再解析で同じ修正が適用される。

## map_loginのsex

0072は19bytesでsexがoffset18、0436は23bytesでsexがoffset22のレイアウトとして分離した。
0436のoffset18をsexとして表示していた169は、別の位置を読んでいた値だった。
同ログの0436はいずれも23bytes、offset22は0。
長さ・sex（0/1）を意味デコードとSEND表示で検証し、未対応の構造を推測して表示しない。
PacketLength.used.txtの0436=23は変更不要で、今回の問題は表示・意味デコードの位置の不一致。

## キャラクター一覧と更新

MARiAの実装を基に099Dは155bytes、0B72は175bytesのレコードとして読み取る。
全長は先頭4bytesを含み、残りがレコード長の整数倍であることを確認する。
4bytesだけの終了通知では、それまで受信した別ページのキャラクターを消去しない。
同一パケット内の重複ID・slot、不正な長さを拒否する。

各レコードからcharacter_id、character_name、base_exp（64bit）、zeny（32bit）、
job_exp（64bit）、slotを取得する。文字列はCP932で検証し、名前だけ壊れている場合は
問題を記録して数値情報を保持する。直前の有効な名前があればそれを残す。
0065で得たaccount IDとcharacter IDの組で保存し、別アカウントへ流用しない。
account未取得の一覧も保存するが、accountが判明したログインへの自動紐付けは行わない。
account未取得の一覧は通信フローごとに分け、同じcharacter IDでも異なる未識別フローを合算しない。

マップログイン時にaccount/characterの両方が一致する一覧から名前・経験値・Zenyを初期化する。
以後、00B0/00B1/0ACBのtype=20はZenyの現在値として更新し、同じキャラクターの台帳にも反映する。
経験値type=1/2も現在値として更新する。通知された増分だと仮定して加算はしない。
Zeny差分は直前の既知残高との差とし、初期値が不明なら差分も不明にする。
各値のパケット番号・フロー等の根拠を保持する。
一覧の再受信では各値の根拠も一覧パケットへ更新する。名前だけ解読できない場合は
直前の有効な名前とその根拠を残す。新しいログインへ値を引き継ぐ際も、一覧だけでなく
最新のZeny・経験値等の個別通知の根拠を引き継ぐ。

同じaccount/characterが別フローへ再ログインした後は、旧フローのZeny・経験値通知や
マップ移動先を、共有台帳・次のログイン先のマップ情報へ反映しない。
旧フロー自身の観測状態には保持し、接続別の記録として参照できる。

マップ情報もaccount/character/出典フローで保持する。所有accountが分かっている情報は
そのaccountに一致するログインだけへ渡し、誤ったログインで消費しない。
account未取得の0071は、character一致候補が1フローだけで、既知の別所有者がいない場合のみ
従来互換の補完候補として利用する。複数の未識別フローに同じcharacter IDがあれば補完しない。

基本データJSONのcharactersに台帳、statesに接続ごとの現在状態を保存する。
基本データウィンドウの詳細にもキャラクター名・ID・BaseExp・JobExpを表示する。
台帳は最大1024キャラクター、accountの関連付けは最大64フロー。取得世代切替で消去する。
既存SQLiteの列は変更しない。GUI保存またはtools.analyze_playerのJSONへ出力できる。

## GUIで台帳を確認する

主画面の「基本データ…」→「キャラクター台帳」で、Account・Slot・Character ID・名前・
BaseExp・Zeny・JobExpを確認できる。一覧のページが受信できれば、マップログイン前でも表示する。
Account未取得は「不明」と表示し、異なる未識別フローの同じcharacter IDも別行に残す。
名前・経験値・Zenyのセルを選択し「選択した値の根拠パケット」を押すと、
その値の最新の根拠へ移動する。他の列では一覧パケットを参照する。
下のJSONにそのキャラクターの値と各値の根拠を表示する。

台帳の行を選んでも、主画面で選択した接続・所持品・現在Zenyは切り替わらない。
台帳は一覧と更新通知をまとめた直近観測値であり、全行がログイン中を示すものではない。
更新で行順が変わっても選択したaccount/characterを保持し、未識別accountでは出典フローも照合する。
取得切替では台帳と選択詳細を消去する。
「基本データJSON保存…」は、選択タブに関係なく接続状態と台帳全体を保存する。
GUI保存・再生時の既存処理と同じストアを使い、再生で別の台帳を推測して作らない。

## 検証

全246テスト通過。account別の同一character ID・未識別フローの分離、再接続後の旧通知抑止、
各値と根拠の同時更新に加え、echoの分割・結合、厳密一致、再接続時の解除、1回限りの消費、
未確認の未知ID停止、ライブと再生の一致、両ログイン形式・不正sex拒否、
一覧のページ終端・重複・長さ・名前異常、account分離、64bit経験値・Zeny更新、GUI表示を確認した。
台帳のログイン前表示、Zeny更新後の値・根拠、行順変更時の選択保持、未識別account行、
接続選択の非変更、JSON保存、取得切替の消去も既存GUIテストで確認した。

同ログの再解析ではverified_account_echoes=2、failed_connections=0、
キャラクター15件、プレイヤー解析問題0件、World解析問題0件。
NPC全29記録がマップ既知。会話1〜2はlasagna.gat、会話3〜6はhal_opera.gatとなった。
過去に記録済みの0xACAC診断は生ログにそのまま残るが、修正後の再解析では停止しない。
entities.json、player.json、dialogues.json、merged-dialogues.jsonと関連MOB・ショップ観測、
Auriga本文を再生成した。パケット番号が増えるため、以前の解析JSONと新しい根拠番号を混用しない。
現バージョンでのWindowsライブ取得は未実施。既存の実機TCP生ログで検証した。
